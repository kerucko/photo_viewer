# PhotoViewer AI flow

Главный агент — оркестратор: он владеет целью итерации, разбивает работу, назначает
исполнителей и зависимости, определяет области записи, принимает решения и отвечает
за финальную приёмку. Остальные агенты выполняют его поручения и общаются друг с другом.
Тестировщик,
продуктовый ревьюер, ревьюер архитектуры/качества кода и автор документации —
обязательные отдельные агенты в конце каждой итерации.
Итерация — один согласованный набор изменений с критериями готовности, а не каждый
вызов инструмента или промежуточное сообщение. Все пути ниже — относительно корня проекта.

## 1. Подготовка оркестратором

- Прочитай `AGENTS.md`, относящиеся к задаче `docs/`, текущий `git status` и diff.
  Отдели уже существующие изменения пользователя от изменений этой итерации.
- Сформулируй результат, критерии приёмки и границы. Уточняй только блокирующие
  продуктовые решения; изучаемые факты выясняй в репозитории.
- Назначь задачи, их зависимости и непересекающиеся области записи; передай каждому
  исполнителю критерии результата и контакты агентов, с которыми нужно согласовать работу.
- Зафиксируй начальный HEAD и состав исходных локальных изменений. Проверяющие должны
  видеть весь результат итерации, включая новые файлы, а не только последний коммит.
- Сообщи пользователю, что применяешь этот навык, и какой этап выполняется.

## 2. Реализация

Создай агента-разработчика через `collaboration.spawn_agent`. Передай запрос,
критерии приёмки, контекст проекта и разрешённые файлы/подсистему. Он реализует назначенные изменения (код, документы или навык)
и необходимые проверки, возвращает список изменений, результаты и ограничения.

Для независимых подсистем можно запустить несколько разработчиков с непересекающейся
областью записи. Для маленькой задачи достаточно одного. Главный агент интегрирует
результат и решает вопросы на границах подсистем, не выдавая собственную проверку за
независимый аудит.

## 3. Финальные проверки отдельными агентами

После завершения реализации останови изменения проверяемого кода и передай всем
проверяющим одно итоговое состояние. Вопросы разработчику допустимы, но его ответы
не заменяют независимую проверку; изменение кода ждёт назначенного этапа исправлений.
Запусти отдельно:

### Агент-тестировщик

- Получает критерии приёмки, итоговые изменения и проектный навык
  `.agents/skills/photo-viewer-build/SKILL.md`.
- Сам выбирает необходимые проверки на основе поведения. Для кода — релевантные
  тесты и сборка; для UI — проверка поведения и обязательная проверка рендера по правилам ниже.
  Для документации/навыков — проверка ссылок, инструкций и сценариев применения;
  итоговая пересборка приложения по разделу 6 обязательна и для таких итераций.
- Не меняет production-код. Новые тесты добавляет только по назначению оркестратора
  в выделенные файлы. Оба ревьюера проверяют также эти тесты в рамках своей роли;
  если тесты добавлены после начала ревью, передай им обновлённый diff.
- Возвращает `PASS`, `FAIL` или `PARTIAL`, команды и их фактические результаты,
  проверенные критерии и непроверенные сценарии. Сборка не равна ручному UI-тесту;
  список поддерживаемых камер не равен декодированию настоящего RAF.

### Агент-ревьюер продуктовых требований

- Независимо читает исходный запрос, критерии приёмки, актуальные требования `docs/`,
  исходное состояние и весь итоговый diff, включая новые файлы.
- Проверяет выполнение согласованных требований: пользовательские сценарии, поведение
  UI, граничные случаи, регрессии и ограничения продукта, включая запрет записи в
  оригиналы. Связывает каждое замечание с конкретным требованием или сценарием.
- Не заменяет тестировщика: успешные тесты не доказывают полноту реализации требований.
  Не добавляет требования и фичи, которых нет в согласованной задаче.

### Агент-ревьюер архитектуры и качества кода

- Независимо читает запрос, архитектуру `docs/`, исходное состояние и весь итоговый diff,
  включая новые файлы; изучает окружающий код для проверки взаимодействий.
- Проверяет границы ответственности, зависимости и разделение UI/каталога/декодирования;
  корректность асинхронности, отмены, потоков и управления памятью, где это применимо.
- Оценивает лаконичность, читаемость, дублирование, уместность паттернов, лишние абстракции
  и code smells. Не навязывает паттерны ради паттернов и не требует рефакторинга вне задачи.
- Для блокирующего замечания объясняет конкретный дефект или нарушение архитектурного
  ограничения и последствия. Стилистические предпочтения и улучшения без такого
  основания оставляет необязательными рекомендациями.

Оба ревьюера работают без редактирования и каждый возвращает собственный `PASS` или
`CHANGES_REQUIRED`. Для замечаний указывают файл/строку, сценарий или нарушенное
ограничение, последствия и необходимое исправление; отделяют блокирующие дефекты от
рекомендаций. Один вердикт не заменяет другой. Для изменений документов/навыков
проверяют соответствующие инструкции и их согласованность в рамках своей роли.

Тестировщик и оба ревьюера могут работать параллельно над зафиксированным состоянием:
оркестратор + три проверяющих укладываются в лимит четырёх активных агентов.
Только тестировщик запускает SwiftPM в общей `.build`; параллельные сборки запрещены.

### Проверка рендера при изменениях UI

- Тестировщик получает рендер **итогового кода** в размерах окна и состояниях,
  существенных для задачи, и передаёт изображения, команды получения, размеры и
  проверяемое состояние оркестратору. Использует синтетические данные; личные фото,
  пути пользователя и локальные артефакты рендера не добавляет в Git.
- Рендер отдельного компонента явно отличает от снимка полного окна. Для изменений
  оболочки окна или toolbar нужен также снимок полного нативного окна: рендер
  компонента не подтверждает системную группировку, отступы и интеграцию панели.
  При недоступности нужного рендера возвращает `PARTIAL` с точным ограничением.
  Сгенерированный дизайн-макет и успешная сборка не являются доказательством рендера.
- После завершения тестировщика и обоих ревьюеров оркестратор создаёт отдельного
  агента анализа изображений **GPT-6 Luna Max** через `collaboration.spawn_agent`
  с `model="gpt-6-luna"`, `reasoning_effort="max"`, `fork_turns="none"`.
  Передаёт запрос пользователя, критерии приёмки, необходимые исходные изображения,
  пути к итоговым рендерам и сведения об их получении: история чата не наследуется.
  Агент открывает изображения через `view_image`, работает без редактирования и
  проверяет видимые требования, включая группировку, отступы, читаемость, обрезание
  и наложение элементов в переданных размерах и состояниях.
- Аналитик возвращает `PASS`, `CHANGES_REQUIRED` или `PARTIAL`: перечисляет просмотренные
  изображения, фактические наблюдения и непроверенные сценарии; для дефектов указывает
  изображение, область, нарушенное требование и нужное исправление. Его отчёт дополняет,
  но не заменяет тестирование и оба ревью. Если указанная модель недоступна, оркестратор
  фиксирует `PARTIAL`; молча подменять её другой моделью нельзя.
- Для изменений только документации/навыков без изменений UI рендер и анализ
  изображений не нужны; явно отметь этот этап как неприменимый.

## 4. Исправления и повторная проверка

При `FAIL` или `CHANGES_REQUIRED` любого проверяющего верни конкретную задачу разработчику через
`collaboration.followup_task`. После исправлений тестировщик повторяет затронутые
проверки, оба ревьюера проверяют обновлённый diff в рамках своих ролей и дают новые
вердикты. Старый PASS не покрывает последующие изменения. Сохраняй проверяемое
состояние неизменным: разработчик правит код только на назначенном этапе исправлений,
после которого запускаются повторные проверки. После исправлений UI тестировщик
получает новый рендер, а аналитик изображений повторяет анализ итогового состояния;
старый рендер и вердикт не подтверждают исправления.

Не превращай предложения по улучшению в обязательные дополнительные фичи. При
внешнем блокере или повторяющейся ошибке сначала выясни причину; не запускай
бесконечные одинаковые попытки. Заверши доступную часть и явно назови блокер.
`PARTIAL` допустим только с перечисленными ограничениями, без заявления о полной приёмке.

## 5. Агент документации и ворклога

После завершения всех проверяющих, включая аналитика изображений для UI, запусти
отдельного агента документации. Передай исходный запрос, окончательные изменения,
отчёты тестировщика, обоих ревьюеров и аналитика изображений (если применимо),
а также нерешённые ограничения.

Область записи: `README.md`, `docs/` и `worklog/`. Другие файлы — только при явном
назначении оркестратора. Не меняет код и не коммитит работу других агентов.

- Обновляет поведение, интерфейсы и инструкции, которые действительно изменились.
- Дополняет `worklog/YYYY-MM-DD.md` по дате пользователя: задача, сделано, роли агентов,
  проверки/результаты, отдельные вердикты обоих ревьюеров и анализа рендера
  (или причину неприменимости), замечания и исправления,
  оставшиеся ограничения. После финальной пересборки из раздела 6 дописывает её
  фактический результат и результат проверки подписи.
- Не выдумывает запуск тестов, ручную проверку, коммит или push. Не записывает личные
  пути, фотографии и секреты. Сохраняет историю и отмечает актуальный итог.
- Возвращает список документов и краткий итог. При незавершённой итерации тоже
  фиксирует выполненную часть и блокер; не пишет «готово» вместо `PARTIAL`/`FAIL`.

Если документация выявила несоответствие коду, оркестратор возвращает задачу на
исправление и соответствующую проверку; затем автор актуализирует итоговую запись.

## 6. Завершение оркестратором

После всех итоговых правок кода, документации и навыков проверь чистоту границ задачи
и назначь тестировщику финальную пересборку из корня проекта:

```sh
./scripts/build-app.sh
codesign --verify --deep --strict --verbose=2 dist/PhotoViewer.app
```

Это обязательный шаг каждой итерации, включая изменения только документации или
навыков: результат — заново собранное `dist/PhotoViewer.app` с проверенной подписью.
Сборка должна соответствовать окончательным исходникам, ресурсам и скриптам сборки;
ранняя сборка не заменяет итоговую. Сборку выполняет только назначенный тестировщик,
последовательно с остальными сборками; `package clean` без отдельного основания не нужен.
При ошибке сборки или проверки подписи зафиксируй `FAIL` или `PARTIAL` с причиной,
не объявляя `dist` актуальным и проверенным.

Передай фактический результат автору документации для итоговой записи в worklog.
Дополнение только отчёта об этой сборке не требует ещё одной пересборки; при новых
изменениях исходников, ресурсов или скриптов сборки повтори её и проверку подписи.

Финальный ответ: что изменилось, чем подтверждено, результат итоговой сборки и проверки
подписи, ограничения и где результат. При блокирующих дефектах не объявляй
итерацию завершённой. Commit/push/публикация выполняются только в рамках действующего
запроса пользователя; навык сам по себе их не разрешает.

## Работа с агентами

- Полным flow управляет только главный агент-оркестратор. Подагент выполняет
  назначенную роль и не запускает flow рекурсивно из-за наследования AGENTS.md;
  дополнительное делегирование допускается только по явному назначению оркестратора.
- Используй подагентов текущего чата, не создавай пользовательские чаты.
- Соблюдай доступный лимит: обычно оркестратор + максимум три работающих подагента.
  Разработчик заканчивает до финальных проверок; при параллельной проверке работают
  тестировщик и два ревьюера. Если нужен ответ неактивного разработчика, оркестратор
  освобождает слот и возобновляет его только для консультации без правок.
  Аналитик изображений начинает после завершения этих трёх проверяющих; автор
  документации — после всех применимых проверок. Лимит четырёх активных агентов
  действует и при повторных проверках.
- В назначении указывай роль, задачу, критерии, файлы для чтения/записи и формат отчёта.
  Агенты делят рабочую папку: не перезаписывать чужие изменения и не выполнять reset/clean.
- Агенты напрямую обмениваются вопросами, контрактами и находками через
  `collaboration.send_message`. Значимые решения, противоречия и блокеры сообщают также
  оркестратору; он разрешает разногласия и утверждает изменения назначения.
- Прямое общение не разрешает расширять scope, менять чужие файлы, назначать работу
  или создавать агентов без явного делегирования оркестратора.
- `send_message` передаёт сведения, но не запускает неактивного агента. Если нужен его
  ответ, сообщи оркестратору: тот возобновит агента через `collaboration.followup_task`
  с конкретным поручением и учётом свободных слотов. Для повторного этапа передай также
  изменения с прошлого прохода. Не подменяй реальные вызовы агентов описанием ролей.
- Если подагенты недоступны, явно сообщи, что независимые этапы не выполнены. Полезную
  работу можно продолжить самостоятельно, но нельзя заявлять выполнение полного flow.
